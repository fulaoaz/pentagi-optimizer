## 1. 要交付什么

用户在一个 PentAGI 产品中管理模型提供商、创建任务、选择执行方式、查看资产与证据、发起复测和生成报告。模型地址与 Key 只需在一个界面维护；运行结果能够追溯到实际执行引擎、任务和证据。

已确定落点为**统一产品、双执行引擎**：继续维护 Optimizer 主线，统一产品层与管理层，先保留两套引擎各自的执行代码和数据库。后续只有在评测证明必要、成本可控时，才迁移具体功能模块。

“统一产品”需要做到统一任务入口、模型选择、结果与权限，不能以一个侧栏链接或两套独立页面作为最终完成标准。也不承诺连接两个引擎就能提高漏洞发现率，效果需通过同条件本地靶场对比验证。

## 2. 已确认的三个决定

| 决策 | 已确认方案 | 对实施的影响 |
| --- | --- | --- |
| 合并深度 | 一个产品、两个可选执行引擎 | 保留 PentAGI 主仓库，通过适配模块持续跟进 ARTEX；避免第一期同时改写两套调度器 |
| 模型共享方式 | PentAGI 统一维护配置，后端同步到受管理的 ARTEX profile | 用户只配置一次，但 ARTEX 会保存密钥副本；需要配置版本、归属和轮换规则 |
| 首版使用范围 | 单一信任域，先面向管理员 | 与目前 ARTEX 实例级凭据相匹配；开放普通用户前必须完成任务授权与隔离验收 |

用户已于 2026-09-24 确认上述三项。统一模型网关、单引擎迁移和多人隔离不纳入首期；以后若需要改变方向，先更新本规划再实施。现有原型继续作为待完善的基础，不视为全部合并目标已经完成。

### 合并深度的取舍

| 路线 | 用户得到的结果 | 主要工作与代价 |
| --- | --- | --- |
| 统一产品、双引擎（推荐） | 一个界面、模型配置和任务/结果中心，按任务选择引擎 | 需要稳定的模型、任务与数据适配；保留两套运行服务 |
| 逐步移植为单引擎 | 最终以 PentAGI 为唯一执行后端 | 逐个重建或合规移植资产、探索、证据、复测能力；必须验证行为，长期工作量较大 |
| 直接合并两套源码 | 将实现整体纳入一个代码工程再重构 | 认证、调度、数据库迁移、前端和依赖均需整合；上游升级及许可证核对成本最高 |

推荐先按功能与数据契约融合。直接合并源码并不会自动统一产品体验；统一产品也不要求立即只有一个进程。

## 4. 推荐架构与职责

| 层次 | 负责什么 | 数据的权威来源 |
| --- | --- | --- |
| PentAGI 产品界面 | 登录、模型配置、任务入口、引擎选择、资产/发现/复测/报告视图 | 通过 PentAGI 后端获取受权限过滤的视图 |
| PentAGI 管理模块 | 用户和项目归属、模型授权、任务提交记录、引擎任务映射、结果归档 | PentAGI 数据库 |
| 引擎适配模块 | 把共同操作转换成各引擎的接口；同步状态与数据 | 按数据类别决定，不能由前端随意指定远端路径 |
| PentAGI 原生引擎 | 现有 Flow、智能体分工、容器执行、记忆与工具调用 | 现有原生运行记录 |
| ARTEX 引擎 | 自身的规划/执行、资产与探索关联、原始证据及复测执行 | ARTEX 运行记录 |
| 统一结果存储 | 归档可验证的结果及证据引用，记录来源和同步时间 | PentAGI 的规范化视图及不可覆盖的证据快照 |

一个执行任务由一个引擎负责。首版创建时明确选择“PentAGI”或“ARTEX”，不启用自动选引擎，也不让两个 planner 同时控制同一个任务。跨引擎移交以后作为新的子任务处理，并显式带入范围、预算和已有证据。

运行数据库初期各自维护，不共用原始表或互相写库。可以统一安装命令、版本清单和备份入口，但不把“一个产品”强制等同于“一个容器”。

## 5. 模型提供商共用方案

### 5.1 用户看到的行为

1. 在 PentAGI 的模型提供商页面维护连接地址、协议、凭据和可用模型。
2. 创建任一种引擎任务时，从同一份有权限访问的提供商列表选择连接和模型。
3. 页面提前说明该组合能否用于当前引擎；不支持的协议或必需参数不能静默丢弃。
4. 提供商改动后显示生效范围：哪些新任务会使用新版本，哪些旧任务仍绑定旧版本。
5. ARTEX 的服务登录令牌仍独立于模型 Key；界面不再把两种凭据混为一谈。

### 5.2 首期方案：配置同步

PentAGI 保存主配置，后端在用户选择后同步到 ARTEX 的专用模型 profile。前端只提交提供商 ID、模型和允许调整的参数，不读取或再次提交已保存的模型密钥。

必要规则：

- 分享前检查提供商所有权和共享授权。能够管理 ARTEX 不代表可以取走其他用户的私有模型 Key。
- 记录 `engine_instance_id + provider_id + config_revision -> remote_profile_id`，重复操作复用映射；不能只按显示名称识别。
- ARTEX profile 的创建、更新与映射写入要串行化并记录结果。无远端幂等支持时，不声称“恰好创建一次”。
- 不通过切换 ARTEX 全局激活模型实现任务选模型；采用任务的 `llm_profile_ids` 绑定。
- 默认把同步 profile 从非显式故障转移池中排除。跨账号或跨费用主体的自动切换必须单独配置。
- 模型、地址和请求参数按运行版本固定。用户编辑产生新版本；已有运行任务不无提示切换模型或端点。
- 密钥轮换、撤销和删除是单独操作：撤销应阻止后续调用；轮换需更新被引用的受管理副本并显示失败项。不能假定删除 PentAGI 一条记录便已撤回 ARTEX 中的副本。
- 正在运行的任务和证据归档引用的配置不能直接硬删除。完成迁移/停用后，再清理远端无引用副本。
- 同步失败不能仍创建任务并退回 ARTEX 全局默认模型。

**边界：这实现“配置只维护一次”，但实际密钥会在两个系统中存储。** 同一 Key 被两个引擎直接使用时，各自的限流器不能构成全局限流器；需要统一统计和费用控制时，使用下一节的网关方案。

### 5.3 可选：统一模型网关

本节是后续扩展设计，用户本次未选择，不进入首期实施范围。

如果目标包含“上游 Key 只保存一份、统一限流/预算/审计”，则在进入模型共享阶段前改选网关方案：

- 两套引擎的受支持模型请求均经过统一网关。只让 ARTEX 走网关而 PentAGI 仍直连，不能称为统一费控。
- ARTEX 获得按实例/项目/提供商/模型限定、可撤销的内部令牌，真实上游 Key 留在主配置存储。
- 网关先支持已验证的 OpenAI Chat Completions 路径，完整处理 SSE、工具调用、取消、超时和错误；不把任意提供商请求粗略翻译为通用文本调用。
- 出站端点和协议由管理员配置决定，客户端不能借请求体改写转发 URL 或授权头。
- 请求发送后发生超时，默认不自动重放；避免重复计费和重复模型输出。任务操作幂等与模型请求重试分别设计。
- 并发请求先预留预算再结算；费用为估算值，实际账单以提供商为准。网关记录为计量主来源，引擎日志只用于关联，避免重复计数。
- 网关故障要有明确不可用状态，不能偷偷直连绕过权限和预算。

此路线工程量更大，但能从机制上集中密钥与调用控制。是否将它纳入首版，由用户确认，不临时加装第三方网关作为默认依赖。

### 5.4 协议和智能体参数

| 内容 | 首批规则 |
| --- | --- |
| OpenAI 兼容 Chat Completions | 第一批支持；需验证模型发现、流式输出、多次工具调用、错误响应和模型名前缀 |
| Anthropic 原生、Responses | 独立兼容阶段；以两边实际发送/接收的字段为验收依据 |
| Gemini、Bedrock、Ollama 原生 | 不自动按 OpenAI 格式同步；有已验证的兼容端点时才开放对应连接 |
| `max_tokens` / `max_completion_tokens` | 显式映射，不能把上下文窗口当输出上限 |
| thinking / reasoning_effort | 支持能力与取值逐项检测；无法表达的必需参数阻止提交并提示 |
| planner / worker / retester | 共用提供商池，但可以采用不同模型和参数；不照搬不同职责的全部配置 |
| 代理、私有 CA、自定义会话头 | 明确支持列表；连通性必须从实际执行服务验证，不能只在浏览器验证 |

ARTEX 的模型 profile API 可创建/更新配置，任务接口可绑定 profile 列表；但复测接口在核对基线中只接收 `notes`，复测智能体又可能有独立模型绑定。**不能据此宣称“任务选的模型必然用于复测”。** 阶段验收必须捕获 planner、worker、retester 的实际模型请求；不支持按任务覆盖时，首版明确展示并统一管理“默认复测模型”，或先完成必要的 ARTEX 接口扩展。

## 6. 任务与结果如何统一

### 6.1 本地任务映射

新增统一执行记录作为产品层入口，不强行复用不相容的原生 Flow 结构。拟保存：本地运行 ID、所属用户/项目、引擎实例、远端任务 ID、模型配置版本、授权范围、预算、同步游标、原始状态、标准状态和最后同步时间。

拟采用的数据记录包括 `engine_instances`、`engine_runs`、`engine_provider_bindings`、`finding_links` 和 `evidence_snapshots`。这是逻辑设计，具体表名和迁移将在实施阶段结合现有 schema 确定。

- 本地提交先有可恢复记录，再调用远端创建接口，最后绑定远端 ID。
- 远端可能已经创建但响应丢失时，状态标记“提交结果未知”，先核对，禁止自动再次创建。
- 状态同时保存原始值和统一值。无法判断时显示“同步未知/连接中断”，不能自动归为失败或完成。
- “暂停、恢复、停止、完成”按引擎真实能力显示。ARTEX 当前的 pause/resume 不能直接伪装为具备与原生引擎相同语义的 stop。
- 任一写操作都先核对本地归属，再解析映射到远端 ID；不允许普通用户直接传任意上游任务 ID。

### 6.2 资产、发现、证据、复测

| 数据 | 合并规则 |
| --- | --- |
| 资产 | 统一项目内身份；按类型、协议、主机、端口、路径等进行规范化，同时保留原始 ID 和来源。不同授权范围不会因资产相同而自动合并权限 |
| 覆盖度 | 保留每个引擎的统计定义与分母；在统一定义完成前不直接相加百分比 |
| 发现 | 首先关联两边的记录；跨引擎疑似重复只提出候选，不自动删除或覆盖其中一条 |
| 证据 | 保存来源引擎、任务/工具调用引用、采集时间、内容指纹和版本；原始记录可追溯，报告内容作安全渲染 |
| 复测 | 新建独立运行记录，包含使用模型、验证条件、结论及证据；“无法确认”不自动变成“已修复” |
| 活动 | 独立游标、去重、断点续取和积压提示；先轮询稳定同步，再决定是否需要 SSE |
| 记忆/知识库 | 初期只共享显式选择的已审核资料。Graphiti 记忆与 ARTEX 探索图不是同一种图，不自动合并或互相喂入全部历史 |
| 用量 | 记录引擎和运行来源；价格版本、缺失 usage、失败请求单列，避免把不完整数据标作准确账单 |

## 7. 权限、运行环境与部署

已确定首版面向单一信任域中的个人/管理员。以后开放普通用户时，需要同时完成项目 ACL、凭据作用域、远端任务映射和结果过滤。仅给页面增加用户字段不能实现多用户隔离。

ARTEX 的资产、工作空间和服务凭据具有实例级特征。对彼此不信任的用户，应使用独立引擎实例/工作空间/凭据边界，或先验证并补齐引擎内部隔离；不能只依靠 PentAGI 页面权限。

PentAGI 的 MCP 限制、容器规则和审批不会自动作用于 ARTEX。统一创建页面要展示本次运行使用的执行环境、目标范围、是否允许写操作及实际可用的控制动作。未完成策略下发验证前，不标示两套执行策略已经等价。

部署保持一个主维护仓库和一个联合安装入口，记录固定镜像版本或 digest。两套数据库独立迁移和备份，数据卷不会在停用引擎时被自动删除。需要备份配置解密所依赖的密钥材料；只回滚镜像不代表数据库结构也可回滚。

ARTEX 的控制登录令牌与模型凭据分开管理，显示过期和健康状态；目前核对到的是登录 JWT，不把签名密钥文件当 API Token，也不默认保存管理员明文密码来续期。正式发行前明确初始化和轮换体验。

### 发布与许可检查

本地 PentAGI 根 LICENSE 为 MIT，核对的 ARTEX 根 LICENSE 为 AGPL-3.0，ARTEX README 另有用途声明。源码移植、修改版发行和联合部署包分别列出组成、来源、依赖与条款核对结果；不会因为服务使用 HTTP 连接就自动判断全部许可问题已解决。此处是待完成的发布检查项，不作法律结论，也不影响当前仅编制规划。

## 8. 实施顺序与每阶段验收

| 阶段 | 做什么、用户得到什么 | 进入下一阶段的验收条件 |
| --- | --- | --- |
| P0：梳理实施基线 | 按已确认方案，把已有原型与其他未提交修改列清，拆分可审查的交付范围 | 三项决策已确定；原型边界、版本及回滚范围明确 |
| P1：验证真实接口 | 固定 ARTEX 版本，启动本地隔离环境，核对认证、模型绑定、任务操作与复测 | 不只依赖 mock；可捕获真实接口往返。尤其明确创建是否可核对、暂停/恢复语义和复测实际选用模型 |
| P2：模型只配置一次 | 建立统一提供商来源和受管理 profile 同步；ARTEX 页面使用同一模型选择器 | 使用同一配置分别跑原生和 ARTEX 测试；验证轮换、错误配置、权限、参数映射、取消和同步失败。同一版本不因重复点击重复建 profile，提交结果未知时先核对，不静默换模型 |
| P3：统一任务中心 | 一个创建入口、统一任务列表、可见的引擎来源、任务映射与状态恢复 | 创建/暂停/恢复、进程重启、断网恢复、重复点击和提交结果未知都可解释且不会重复执行；越权访问被拒绝 |
| P4：统一资产与证据 | 项目资产、发现关联、证据详情、复测与报告放在一套工作流里 | 任意结论可追溯到来源和证据；两个引擎的 ID 不冲突；复测不会覆盖原始证据；分页与恢复不漏记录 |
| P5：试运行与发行 | 固定版本联合部署、备份与回滚，完成本地靶场对比和发布文档 | 升级/恢复演练成功；许可与依赖核对完成；核心交互、原生功能和相同条件对比通过 |

若选择统一网关，P2 应拆成“协议透传验证、两套引擎接入、统一计量与限额”三步；不能把它估作一次简单 profile 同步。若选择多用户首发，P3 的归属和隔离必须前置到 P1/P2 之前。

## 9. 统一验收场景

- 模型：配置一次，两套任务均使用被选择的实际模型；错误令牌、不可表达参数和协议不兼容有明确提示。
- 模型更新：地址/模型变更不无提示影响已运行任务；撤销和轮换能验证后续请求行为。
- 凭据：页面、错误、日志、导出和遥测中无模型 Key；不同用户的私有连接不会被管理员操作顺带同步。
- 可靠性：重复提交、上游收到请求后断连、重启、超时、令牌过期均不引发自动重复创建或错误完成状态。
- 数据：同一资产跨引擎可关联，不同项目保持隔离；大结果分页完整；断点同步可恢复。
- 复测：保留原证据，记录每轮验证条件与结论，核对实际使用的模型；“无法确认”不会自动关闭发现。
- 回归：已有原生 Flow、提供商保存/解密/模型列表、中文/英文界面、MCP、资源与知识库功能保持可用。
- 效果：在同一批本地靶场上固定模型、范围、时间/Token 预算，记录可复现发现、误报、耗时、成本和人工介入。仅把观察到的结果写进发布说明。
